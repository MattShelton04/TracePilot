# Session catalogue and engine metadata semantics

This audit describes production source at `d95f6d81d8a27f9ee3b18967f00b81d76c25e723`. Pending performance PRs are separate proposals, not evidence of production behavior. It covers 61 current application columns across six tables and 16 engine metadata columns across four engine tables. Seven engine columns belong to schema/sequence in the reconstructed schema; the nine statistics columns belong to optional engine objects that are also present in this validated snapshot. The complete per-column machine-readable record is [semantics-catalogue.json](semantics-catalogue.json). Other analytics/search tables are covered by the companion audit sections. The validated snapshot has 31 tables / 238 table_xinfo columns, including sqlite_stat1/stat4. The full [statistics](statistics.md) and [storage](storage.md) reports provide measured aggregates; dispositions incorporate this population without implying physical drop-column savings.

`KEEP` retains the current purpose. `CHANGE` means clarify or correct a semantic/operational contract, not immediately change DDL. `CONSOLIDATE` identifies redundant projection after full writer/reader/consumer tracing. `DEPRECATE_REMOVE_CANDIDATE` requires compatibility evidence and an actual deprecate-read release before a later drop. `INSUFFICIENT_EVIDENCE` identifies a diagnostic/reserved contract without enough evidence to retire it. No removal recommendation follows from a text-search miss or zero population alone.

## Ownership, snapshot and atomicity contract

The provider snapshot is authoritative; SQLite stores derived replaceable views, plus the source locator/owner needed to reopen the authoritative input. A successful metadata savepoint replaces parent fields and all analytics children together. Failed preparation or session savepoint preserves last-good data. Search content stays available while metadata updates: search has its own successful fingerprint/version/timestamp and its own transaction. Fingerprints compare captured file metadata and provider version tokens, not cryptographic hashes of file content. Equal mtime/size after an external edit can therefore evade metadata-only fingerprint detection.

Metadata preparation passes cancellation into provider reads and checks the fingerprint again before writing. The enclosing batch rolls back on stale source generation before commit; source prune/purge checks the generation after deletes hold the write lock. Pruning runs only with a complete source inventory. Prior committed batches remain committed when a later batch stops. These boundaries protect source ownership; they do not make the whole corpus or both extraction phases one transaction.

Two source risks merit targeted reproduction before a code change: metadata batch indexing catches individual errors without search batching's `is_autocommit()` guard, so an SQLite error that auto-rolls back the outer transaction may let later session savepoints commit alone. The shared `with_transaction` manually uses BEGIN/COMMIT/ROLLBACK and has no scope guard for a panic or commit error, despite its panic-safety comment. These are source findings, not observed failures in this audit.

## Readers, decoders, IPC and export

List/search session projections name 18 columns and decode by column name. Locator lookup reads path/source/role/parent using positional decoding; it validates stored enums and falls back to provider resolution when a newer enum or unavailable index prevents a usable locator. Providers trust a stored locator only within the enabled source's current root. Unknown source names cause list row conversion errors; source aggregates skip unknown names. Analytics use explicitly ordered SELECT expressions with positional tuple decoding. Their query helpers dynamically compose bound date/repository/source/hide-empty conditions; candidate decisions include those helpers, joins, aggregates and field projections.

`SELECT *` appearances in search query-builder examples/tests do not imply production all-column reads of these tables. Generic golden snapshot code does introspect every table/column, so it is a compatibility/test consumer even for fields absent from production projections. The session list IPC transforms optional signed counts to optional usize; the detail command reopens provider source and does not treat persisted analytics totals as authoritative detail. `get_session_incidents` reads normalized detail, parses raw JSON for IPC and feeds the cached frontend section. Tool Analysis and Code Impact consume their materialized aggregates through analytics commands/client/store/views.

Export resolves selected session IDs through stored locator/provider registry, then loads provider files/snapshot and calls `export_inputs`; it does not dump the index.db rows, fingerprints or incident cache. Raw source session databases exported as custom tables are a different artifact. Whole-database backup/restore remains a generic storage consumer and must preserve schema, engine allocator state, FTS consistency and WAL contents.

## Migration and compatibility

The current index plan is versions 1–11, 13–25; v12 is intentionally absent. `schema_version` MAX(version), not PRAGMA user_version, gates migrations. Each body/pre-hook and version row share a transaction; configured on-disk backups use SQLite online backup before migration. Old applied_at addition can fail and is tolerated; timestamps are not a migration correctness gate. Search progress columns are idempotent hooks plus an every-open fixup. v13 dropped health_score; v14 added copilot_version and removed has_plan, has_checkpoints, checkpoint_count, shutdown_type, duration_ms, warning_count, last_error_type and last_error_message. Those historical columns are absent from current catalogue; no new removal is proposed here.

v21 added independent successful snapshot fingerprints; NULL forces refresh. v22 backfilled existing rows as Copilot/primary/visible. v24 kept USD separate from premium-request cost. Schema changes follow [ADR 0013](../adr/0013-db-migration-policy.md): forward-only, deprecate reads before later column removal, and explicit export/import handling for breaking semantic changes. [ADR 0003](../adr/0003-sqlite-wal-per-feature-databases.md) contains historical claims about user_version and per-feature databases that do not describe this production index accurately. This catalogue follows the source.

## Rowids and engine tables

These ordinary application tables are rowid tables. `sessions.id` and composite TEXT/integer primary keys in activity/modified_files are separate indexes over implicit rowid storage. The session rowid is a functional external-content FTS join key, not redundant baggage; ON CONFLICT UPDATE retains it and insert/update/delete triggers synchronize `sessions_fts`. Rebuilding sessions as WITHOUT ROWID or replacing rows with INSERT OR REPLACE would require an explicit FTS identity redesign. Incident id aliases its rowid and may be reused after replacement. schema_version and maintenance_state also have implicit rowids; neither is an application-visible identity.

`sqlite_schema`/`sqlite_master` describes objects and cannot be counted as a second physical table merely because both aliases are queried. sqlite_sequence maintains search_content AUTOINCREMENT high-water mark. Planner tables are engine-generated, optional and not session analytics. sqlite_stat4 sample BLOBs may contain private values, so publish aggregate byte/count evidence only. Keep engine ownership; do not hand-edit these tables or infer unused columns from missing Rust reads. The exact observed engine objects/compile options must come from snapshot introspection. Definitions follow [SQLite schema documentation](https://www.sqlite.org/schematab.html) and [SQLite file-format documentation](https://www.sqlite.org/fileformat2.html#internal_schema_objects).

## Known semantic boundaries

- Activity storage is UTC Monday-first, timestamped reconstructed calls only. The frontend shifts this aggregate grid by the current browser time-zone offset for local display; it cannot apply historical daylight-saving offsets per call because dates are absent. Its date filter selects sessions by last activity rather than each call's occurrence date; weekday/hour storage cannot support exact historical range clipping. Keep table while treating event-date analytics as a separate design.
- Modified file identity is exact source spelling per session; aggregate slash normalization merges the same relative path across repositories and does not normalize case. Most-modified-file `additions` is currently number of sessions, with `deletions=0`, not line counts. Clarify the API/presentation before changing file identity.
- Detailed incidents are capped at the first 100 qualifying events; parent incident counters include all events. Never compare row count directly to lifetime error totals or derive compaction token totals from the capped cache.
- USD, premium requests, legacy premium cost and observed nano-AIU are different quantities. NULL/zero distinctions and partial source coverage must survive any consolidation. No source-independent grand currency total follows from these columns.
- `hidden` is written from role but not applied by ordinary list/analytics/search readers; source providers currently advertise no hidden roles. `source_format_version` remains None in normal preparation. These are reserved compatibility decisions, not proven storage leaks.
- The maintenance epoch advances after any successful sub-operation (including a merge with no remaining work), not completion of every operation. `wal_checkpoint(TRUNCATE)` is executed without decoding busy/checkpoint result tuples. These throttle/diagnostic semantics should be clarified before using the epoch as a completion certificate.

## Measured catalogue evidence and candidate scale

The validated snapshot contains 729 sessions: 619 Copilot and 110 Claude Code. Every declared column in this catalogue has complete exact population/type/value-length statistics, linked in its rationale. The snapshot has 1,254 activity buckets, 5,719 modified-file rows and 1,003 incident details; incident JSON is preserved for the active drill-down contract. Its incident table allocates 12,148,736 bytes, including 10,108,928 overflow bytes, while the sessions table B-tree alone allocates 786,432 bytes. These are measured physical allocations, distinct from logical text sizes or removable-field savings. All measured FK, empty-search-content, bucket bounds, known-source, tool outcome/duration-count, timestamp-order and JSON checks returned zero violations; all inspected timestamp fields parse. [Statistics](statistics.md), [storage](storage.md) and [methodology/provenance](methodology.md) document the scope.

The 211 Copilot sessions with NULL event/turn/tool counts and event metadata can be legitimate metadata-only entries; source availability and NULL contracts must be checked before describing them as failures. All sessions have successful search markers, but 219 have no search rows: 217 Copilot (211 unavailable event counts plus six with positive turns) and two Claude sessions with zero turns. Successful empty extraction explicitly stamps the marker; turns can contain no eligible searchable content. This is not evidence of corruption. No catalogue field is removed or reclassified solely because it is NULL, constant or sparse in this installation.

The metadata/search fingerprint strings differ in all 619 Copilot rows and match in all 110 Claude rows. Copilot intentionally stores the full workspace/events fingerprint for metadata and the events projection for search; the generic source can use the same full serialization for both successful phases. String equality does not prove current on-disk source freshness, and inequality does not prove drift. This audit did not compare the snapshot's fingerprints with current source files.

The two redundant mtime projections carry 39,429 logical text bytes together (21,455 workspace + 17,974 events). Their known maximum 35-byte UTF-8 lengths use one-byte SQLite serial codes when present, so their own serial-entry contribution is at most 1,458 bytes together. Compaction input/output candidates each have 549 zero and 180 positive values; their observed ranges fit up to three value bytes per positive integer. Across both columns this bounds direct positive-value payload at 1,080 bytes and serial entries at 1,458 bytes if present. These are field-component bounds only: actual record layouts, record-header-length changes, page packing, freelist reuse and vacuum outcomes have not been decoded or measured. They are not promised file reductions.

All-NULL source_format_version and all-zero hidden have zero value payload; each contributes at most 729 one-byte serial entries if present, possibly less when added/trailing fields are absent from older records. Their reserved contract therefore remains INSUFFICIENT_EVIDENCE, with negligible potential direct storage benefit. `indexed_at` has 13,851 text bytes but preserves diagnostic chronology, also insufficient for retirement. `events_size` retains an active size-selection diagnostic consumer. [SQLite record format](https://www.sqlite.org/fileformat2.html#record_format) defines serial codes and integer payload widths. Any removal still needs ADR 0013's reader deprecation, support-tool compatibility inventory and a later migration; no DDL change is made by this audit.
